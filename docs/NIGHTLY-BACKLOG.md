- [ ] 2026-08-26 — **The write guard lets a caller-supplied variable value change a rule's glob semantics, and a deny rule with an unresolved variable fails open** — two defects in `lib/agent-runtime/paths.mjs`, which has **zero prior nightly commits** (it is untouched scaffold code), found while auditing the `assertWriteAllowed` chain. Not patched: both share one root cause and the correct fix is structural, not a patch to either symptom.
  - (a) **Glob widening via a variable value.** `expandVars` substitutes into the *pattern string*, and `globToRegex` then interprets the result — so metacharacters inside the substituted value are read as glob syntax. Reproduced against `planning-agent`'s real rule `wiki/projects/{{project}}/decisions.md`, target `wiki/projects/SOMEONE-ELSES-PROJECT/decisions.md`: `project: "my-project"` → denied (`not in allowed_writes`); `project: "*"` → **allowed**; `project: "**"` → **allowed**. The value is caller-controlled and unvalidated — `closeTask` does `vars = { project: payload.project || null }` straight from the MCP tool argument / route body, and the MCP schema is a bare `{ type: 'string' }` (contrast `mcp/server.js:1167`, which does run `validateSlug` on `args.project` for the rewrite path). **Currently latent, and that is the only reason this is not urgent:** `_planWrites` derives every file path from `contract.agent_id`/`contract.tier`, so no planner emits a `wiki/projects/{{project}}/…` path today and the widened rule is never the rule that decides a write. It becomes live the moment any planner emits a project-scoped path.
  - (b) **A `forbidden_paths` rule with an unresolved variable denies nothing.** When a var is missing, `expandVars` leaves the literal `{{name}}`; `globToRegex` escapes `{` and `}` as regex literals, so the rule matches no real path. For `allowed_writes` that is fail-closed and fine. For a deny rule it is fail-open. Reproduced: contract with `allowed_writes: ["wiki/**"]` and `forbidden_paths: ["wiki/projects/{{secret}}/**"]`, called with empty vars, writing `wiki/projects/classified/notes.md` → `allowed: true, reason: "matched allowed_writes"`. No shipped contract puts a variable in `forbidden_paths` today, so blast radius is currently zero.
  - Why not patched tonight: the obvious fix — escape metacharacters in the substituted value — **cannot work**, because `globToRegex` has no escape mechanism. It converts `\` to a literal backslash in the output regex, so `\*` becomes `\\` followed by `[^/]*` and matches *more*, not less. `[*]` fails the same way. There is no string `expandVars` can emit that `globToRegex` will read as a literal asterisk. The real fix is to stop expanding into the pattern string at all: build the regex in one pass (`globToRegexWithVars(pattern, vars)`) that glob-converts the literal chunks and `RegExp`-escapes the substituted values, and return the set of unresolved variable names so the caller can fail closed on a deny rule. That replaces `expandVars`+`globToRegex` at all four call sites (`paths.mjs` ×2, `context-loader.mjs:93`, `vault-writeback.mjs:30`) — the central write chokepoint, which wants a measured blast radius and a fixture, not a 3am rewrite. Note (b) additionally needs a policy call from Jay that is not a code question: an under-specified deny rule failing closed means it blocks *every* write until the variable is supplied.
