Avoid it for one-off, low-stakes tasks where a single prompt-response is sufficient — the overhead of building phases, envelopes, and gates isn't worth it if you don't need to run the workflow more than once.

## Structure
The core idea, drawn from the "Super Simple Software Factory" (SSSF) project: **deterministic code owns the graph; coding agents are bounded nodes inside it.**

- **Deterministic orchestrator script** (in SSSF, an "ADW" — AI Developer Workflow — script) owns sequencing, retries, and acceptance criteria. This is plain code, not a prompt.
- **Named phases** are the unit of execution and of the trace — e.g. engineer, planner, builder, reviewer phases laid out on a timeline.
- **Typed JSON envelopes** carry context across the seams between phases, rather than relying on an agent's own memory/transcript.
- **Gates** define what \"done\" means for each phase — an explicit, checkable acceptance criterion rather than \"the agent stopped talking.\"
- **Event stream to a trace store** (SQLite in SSSF) records every event as it happens, giving a queryable, replayable audit trail instead of a transcript you read like a novel.
- **Correction is cheaper than restart**: because the session inside a phase stays alive, you can correct within a phase rather than cold-starting the whole run.

## Example
From the source project's framing: a single large agent given the whole SDLC has no phase boundary and no nameable acceptance criterion, so failures are invisible and reruns produce different systems each time. SSSF instead wraps this as one installable \"skill\" stamped into any repo, where an ADW script drives an engineer → planner → builder → reviewer sequence. Every phase transition and event streams into SQLite, and a UI polls that trace DB to show progress as a swimlane (one phase running, the next queued).

> "A software factory does one thing: it gives you more leverage on your prompt... **Agent proposes, code disposes.**" — Super Simple Software Factory README

## Trade-offs
**Pros**
- Failures are localized to a named phase instead of an opaque end-to-end run.
- Retries/corrections resume rather than cold-start, preserving agent context already gained.
- Acceptance criteria (gates) make \"done\" objective and auditable.
- Full event trace enables debugging and post-hoc evaluation without re-reading transcripts.

**Cons**
- Requires upfront investment in building the orchestrator, envelope schemas, and gates — more engineering overhead than \"just prompt the agent.\"
- Rigid phase boundaries can be a poor fit for genuinely exploratory or ill-defined tasks.
- The pattern shifts control (and risk of bugs) into the deterministic code layer — that code itself now needs testing and maintenance.
