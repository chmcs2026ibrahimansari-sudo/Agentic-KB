# Mission Control / Governed Autonomous Software Factory

## Definition
Jay's internal term for the overall control plane he is building: a "governed autonomous software factory" in which work flows through a defined pipeline of subsystems, each with verification and governance checkpoints, so that agentic work can be trusted to run with increasing autonomy over time.

The canonical pipeline (as of this note) is:

```
Mission → Plan → recipe recommendation → Factory Version → Context Package →
worker lease → sandbox/local execution → trace/observability → source Attempt →
candidate PR → independent verification Attempt → exact Verification Subject →
frozen Verification Plan → evidence/receipts → exact-current eligibility →
human acceptance → Factory Learning signal generation → improvement candidate →
experiment proposal
```

Key nouns/entities in this system (each likely a first-class concept elsewhere in the KB or worth defining later):
- **Mission** — top-level unit of intent that enters the system
- **Plan** / **recipe recommendation** — how a Mission is decomposed into executable work
- **Factory Version** / **Context Package** — versioned bundle of state/config handed to a worker
- **Worker lease** — a claim a worker holds while executing work (can go stale)
- **Attempt** — a discrete execution instance (source Attempt vs. independent verification Attempt)
- **Verification Subject** / **Verification Plan** — the exact thing being verified and the frozen plan used to verify it
- **WorkOrder** — the only governed mechanism allowed to mutate production/config
- **Learning Signal** — a repeated correction or pattern detected and fed back into the system

## Why It Matters
This is the architectural backbone that other patterns — [Factory Learning Loop](../patterns/pattern-factory-learning-loop.md) and [System Qualification Run](../patterns/pattern-system-qualification-run.md) — operate within. Anything discussing governance, verification, or learning in Jay's stack should be understood as a subsystem of this larger pipeline.

A core design principle stated in the source note: improvement candidates generated by learning **cannot directly change production/config** — they must go through a governed WorkOrder. This is the primary safety invariant of the whole factory.

> "That's where you'll know you've moved from 'many strong components' to an actual governed autonomous software factory."

## Example
A single Mission traverses the entire pipeline above, including deliberately injected faults (stale worker lease, candidate/PR-head mismatch, verification failure, context miss, deterministic gate failure, sandbox orphan, model-routing override) to prove the system's invariants hold not just on the happy path but across subsystem boundaries.
