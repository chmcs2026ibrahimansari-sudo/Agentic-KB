# Harrison Chase — DeepAgents Backend/Sandbox Separation

## Source

- Raw source: `raw/framework-docs/x-twitter-2089029054611837324.md`
- URL: https://x.com/hwchase17/status/2089029054611837324
- Captured context: Jay flagged this for backend/sandbox separation, filesystem-like agent state, local/cloud UI split, MCP/A2A deployment, and the “brains vs hands” boundary.

## TL;DR

Harrison Chase describes DeepAgents as an agent loop connected to a separate backend that exposes filesystem-like operations, optionally plus sandboxed execution, allowing the same agent brain to run behind local TUIs, cloud UIs, Slack, or non-coding workflows.

## Key Points

- **Backend as file-like state:** The backend must expose read/write/edit operations, but the implementation can be a real filesystem, database, or object storage.
- **Sandbox as backend variant:** A backend becomes a sandbox when it also exposes an `execute` command for code execution.
- **Brain/hand separation:** The agent loop is separate from the execution substrate, matching Anthropic's managed-agents framing of separating reasoning from action.
- **Multiple frontend shapes:** The same architecture can power a local TUI coding agent (`dcode`), a cloud coding experience backed by LangSmith deployments plus remote sandboxes, web and Slack frontends connected to the same backend, or non-coding agents with a fake backend.
- **Deployment surface:** DeepAgents is built on LangGraph, which the source says makes MCP, A2A, and other endpoint deployment paths easier.

## Jay-Relevant Takeaway

This is the MissionControl shape worth preserving: one governed orchestration/control plane can attach to local, cloud, Slack, or UI fronts if the execution backend contract is stable and the brain never directly owns the sandbox implementation.

## Caveats
